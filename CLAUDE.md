# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Personal homepage/blog (lkwplus.com) built on the `astro-erudite` v2 template: Astro 7, **no UI framework and no CSS framework** — native CSS with autonomous custom elements and Utopia fluid scales. Package manager is **bun** (`bun.lock`); Node >= 22.12.0.

## Commands

```bash
bun dev              # Dev server at http://localhost:4321
bun run build        # Build static site to dist/
bun run preview      # Preview the production build
bun test             # Unit tests (src/lib/client/*.test.ts, bun:test)
bun run check:links  # Static internal-link check over dist/ (build first)
bun run format       # Format with Biome (writes)
bun run format:check # Check formatting without writing
bun run astro ...    # Astro CLI (e.g. `bun run astro check`)
```

`bun dev` and `bun run build` first run `scripts/prebuild.ts`, which syncs the self-hosted Umami tracker into `public/headache.js` and downloads a random cat photo to `src/assets/cat.jpg` (both gitignored; they fall back to the committed `src/assets/headache-fallback.js` / `src/assets/cat-fallback.jpg` when offline). Both steps are non-fatal on network failure.

`src/assets/fonts/og/` holds **subset** Noto Sans SC woffs for build-time OG rendering (all GB2312 hanzi + kana + punctuation + every character in current content). If a new post title needs a character outside that set, re-run `bun scripts/subset-og-fonts.ts` — it re-subsets from the pristine full fonts pinned in git history, so it is safe to run repeatedly.

There is **no linter** — Biome runs format-only (linter and assist disabled in `biome.json`). The automated checks are formatting (`bun run format:check`), type checking (`bun run astro check`, strict tsconfig), unit tests (`bun test`, covering the pure data helpers in `src/lib/client/`), and a post-build internal-link check (`bun run check:links`, `scripts/check-links.ts` — verifies every internal href/src/srcset and `#fragment` in `dist/`, and the same for `[](…)` targets in the Markdown artifacts, where a surviving relative path means an image that only resolves from the source tree); CI (`.github/workflows/ci.yml`, actions pinned to SHAs) runs all of them. `@astrojs/check` requires TypeScript 6.x — the pinned `typescript@^6` devDependency must not be bumped to 7 until the native compiler exposes the programmatic API. A `.githooks/pre-commit` hook formats staged files via Biome on every commit (installed by the `prepare` script on `bun install`). Biome style: double quotes, semicolons as-needed, 2-space indent, 80 cols.

## Architecture

**Central config — `src/consts.ts`.** The personalization surface. Exports `SITE`, `NAVIGATION`, `SOCIALS`, the feed endpoints (`MASTODON`, `SWITCH`, `FLIGHTS`, …), `USES`, and `PROFILE_TABS` (the multi-language code tabs on the homepage). Edit here before touching components.

**Path alias:** `@/*` → `./src/*`.

### Markdown pipeline (the non-obvious part)

This site does **not** use remark/rehype. Markdown is processed by **Sätteri** (a Rust processor) configured in `astro.config.ts` with `syntaxHighlight: false`. Custom transforms live in `src/lib/` and come in two kinds, both registered in `astro.config.ts`:

- **mdast plugins** (`defineMdastPlugin` from `satteri`) operate on the Markdown AST → `callout.ts` (`:::note` GitHub-style callouts), `math.ts` (`$…$`/`$$…$$` → MathML via **Temml**, not KaTeX), `expressive-code/inline.ts` (inline `` `code{:lang}` ``).
- **hast plugins** (`defineHastPlugin`) operate on the HTML AST → `external-links.ts`, `expressive-code` block rendering, `heading-namespace.ts` (subpost-scoped heading IDs), `heading-anchors.ts` (clickable `#` permalinks).

When adding a Markdown feature, write a `define{Mdast,Hast}Plugin` and add it to the corresponding array in `astro.config.ts` — do not reach for unified/remark packages.

**Code blocks** use Expressive Code via `satteri-expressive-code`. `src/lib/expressive-code/render.ts` exposes `renderCodeBlocks()` so code can be rendered **outside** Markdown (used by `CodeTabs.astro` and the homepage `PROFILE_TABS`), reusing the same theme/renderer as blog posts.

### Content collections (`src/content.config.ts`)

Three glob collections: `blog`, `authors`, `friends`. The glob pattern `**/[^_]*.md` means **any file or folder prefixed with `_` is ignored** (use for drafts/partials).

**Posts and subposts/series** is the key convention:
- A post is a folder under `src/content/blog/<slug>/` containing `index.md` (the parent), plus a colocated `assets/` dir for images (`image: ./assets/…`).
- Sibling `.md` files in that folder are **subposts**. `isSubpost(id)` (in `src/lib/utils.ts`) = the id contains a `/`.
- Subposts form a **series** rendered as one continuous scrollable document. `src/lib/content.ts` provides `getPosts()` (top-level only), `getSubposts()` (grouped by parent, ordered by `order` frontmatter then date), and `getTags()`.
- The route `src/pages/blog/[...id].astro` builds the parent + subpost chain into a single page with a unified table of contents. The sitemap filter in `astro.config.ts` excludes subpost URLs and tag pages.
- `src/pages/blog/[...id].md.ts` serves every entry's own source at `/blog/<id>.md` — reconstructed frontmatter (`postMarkdown` in `src/lib/content.ts`) plus the body, one file per entry rather than one per chain. The body is not raw: an artifact served at `/blog/<id>.md` sits a directory above the source it was built from, so `postMarkdown` rewrites every colocated `./assets/…` target to its published URL. It resolves them through a **lazy** `import.meta.glob` over the collection's images and asks `getImage()` for the transform with no options — the same one the Markdown pipeline requests for a bare `![](./…)`, so the export points at the very asset the page already emits rather than a second copy. The cost of the glob is that colocated images *no page references* now ship at full size; eager-importing them instead makes that unconditional, which is why the glob stays lazy. `CopyMarkdown.astro` sits at the far end of each article's meta row (`margin-inline-start: auto` — it is an action among metadata, so it is pushed away from the byline) as a chip reading `Copy Markdown` behind the Markdown mark (`src/assets/icons/markdown.svg`), beside an arrow that opens the same URL in a new tab. It is a soft `--muted` fill with no border — an object in the row rather than a form control — split by one hairline. The label is fixed text rather than the artifact's filename, which a long slug would ellipse. The markdown is fetched on hover/focus so the clipboard write stays inside the click's user activation. Confirmation is the mark cross-fading into a check in place, so the chip never changes width; the result is announced through a visually hidden `aria-live` span, and the text is deliberately *not* brightened, which would read as a hover stuck on after the pointer has left. `MetaPost.astro` advertises it as `<link rel="alternate" type="text/markdown">`. `/llms.txt` (`llms.txt.ts`) indexes those `.md` URLs per [llmstxt.org](https://llmstxt.org), and `/llms-full.txt` concatenates them.
- `TableOfContents.astro` heads the desktop rail with a reading-progress ring and its percentage, and the collapsed mobile bar with the same ring at glyph size. One `--progress` custom property on the `nav` drives both, so the scroll handler writes one value and neither ring knows about the other. Several entries carry `data-active` whenever their blocks share the viewport; only the first also carries `aria-current="location"`, which is what takes the extra font weight — so exactly one line reads as "you are here". The ring, not a title fading in once the `h1` scrolls off, carries that information, because a title would grow the rail by a line mid-scroll.

Blog frontmatter: `title`, `description`, `date`, `authors` (refs into the `authors` collection) are required; `tags`, `image`, `order`, `draft`, `mermaid`, `ai` optional. `ai: true` marks a post as AI-assisted, and the disclosure lives **in the byline** (`Byline.astro`, shared by `BlogCard.astro` and the post header), because it is a statement about authorship: the assistant takes a place in the avatar stack as a dashed-outline disc with a filled sparkle (`src/assets/icons/sparkle.svg`) — the same disc as a person's, plainly not somebody — and the names read `lkw123 with AI`, the `with AI` a shade dimmer than the name. In the list it is a `title` tooltip; in the post header (`interactive`) it is a button (no underline; `cursor: help` and a hover colour are the affordance) opening a native `popover="auto"` note — `Drafted with an AI assistant.` under an `AI-assisted` heading with the Claude mark (`src/assets/icons/ai/claude.svg`) — anchored beneath it by CSS anchor positioning (`anchor-name`/`position-anchor` set inline per byline, `id` unique per article since a series renders several; `justify-self: anchor-center` keeps it inside the screen margins, and without anchor support it falls back to the UA's centred popover). Write `popover="auto"`, not a bare `popover`: Astro renders the bare boolean as `popover="true"`, an invalid value that falls back to the *manual* state, so the note would not light-dismiss on an outside click.

The post page's byline row therefore holds only what identifies the article — author (and the AI co-author, when there is one), the dates, and the Copy Markdown chip. The dates are `PostDates.astro`: one date, or — when `updatedDate` differs — a span from publication to the latest revision (`Jun 16 ⇢ Aug 20, 2026`, the first date dropping a year the second already states) joined by a dashed arrow that marches toward the newer date on hover, the latest date at full `--foreground` since it is the one that says how current the post is. Both phrases sit on the element's `title` and in visually hidden text. **Tags sit on a row of their own** (`PostTags.astro`), the last thing in each article's `header` — set a `--space-s` apart from the meta row, and the header's bottom margin tightened (`header:has(post-tags)`) so they sit nearer the body they index than the byline they follow — a dimmed `#tags` line, which is what keeps the byline row from crowding on a post with five tags. After `prose-content`, nobody would scroll to them.

`reset.css` blockifies `svg` (Preflight-style), so any element mixing an icon with text on one line has to be `inline-flex` — `post-dates` and the `CopyMarkdown` segments both are. An icon dropped into an inline context silently stacks above its label instead. `draft: true` posts are filtered out by `getPosts`. `mermaid: true` opts a post into Mermaid diagrams: it makes the `mermaid.ts` mdast plugin turn ```` ```mermaid ```` fences into `<pre class="mermaid">` and gates the client-side `Mermaid.astro` script in `src/pages/blog/[...id].astro` (any post in a series chain opting in loads it for the whole page); without the flag, fences render as plain code blocks.

### Styling

All CSS is hand-written in `src/styles/*.css` and imported, in cascade order, at the top of `src/layouts/Layout.astro` (single shared layout). Conventions:
- **Radix Colors** hex scales in `color.css`, each step a `light-dark()` pair behind semantic tokens (`--background`, `--foreground`, …); derived tints elsewhere use `color-mix(in oklab, …)`.
- **Utopia** fluid type/space scales: `--step-*` (font sizes) and `--space-*` (spacing). Use these tokens rather than hardcoded px/rem.
- **Autonomous custom elements as layout primitives** — `<page-grid>`, `<page-nav>`, `<post-meta>`, `<dictionary-entry>`, `<movies-feed>`, etc. are styled by element selectors, not class names. Component-local styles go in the `.astro` file's `<style>` block.
- The layout is a 12-column grid (sidebar / content / TOC) that collapses to a single column below `64rem`.

### Notable runtime behavior

`Movies.astro` (on `/misc`) fetches recent Letterboxd films **client-side at runtime** from an external embed endpoint, with skeleton loading and a fallback — it is not build-time data. `Music.astro` (also on `/misc`) does the same against the self-hosted Koito instance (`https://music.lkwplus.com`, public read API): all-time stats, a listen-activity heatmap, and the last played tracks. `Tokens.astro` (on `/tokens`) renders an AI-token-usage dashboard the same way from a single precomposed endpoint (`https://tokens.lkwplus.com/api/site`, open CORS, `Cache-Control: no-cache` + strong ETag — the browser revalidates every load and an unchanged payload is a ~0-byte 304) served by the sibling `tokens-worker` repo — which also owns the canonical model/provider id mapping (per-effort model variants merged; provider ids resolved to model vendors server-side by the model name — a Claude model via Zed's `zed.dev` counts as `anthropic`, GLM via OpenCode zen as `zai`, DeepSeek through a self-hosted `gpt-load` pool as `deepseek` — with the reported id surviving only for models the rules can't place, so a proxy the user names in some client config never becomes a row of its own): a **Quota** section first, since what is left of a subscription is the one thing on this page with a deadline on it, with one card per subscription side by side — Codex and Claude, each read from its own vendor by its own collector on the same host, the only part of the page drawn from *reported* rather than derived data. Every card is built to admit its own age: each carries its own `capturedAt` (two collectors on two timers are two different answers to "how old is this") shown beside the plan name and turned red past two hours; every window always renders head (`xx% used`), meter and foot — an unanchored one says `starts on first use` rather than going blank, so rows line up across the two cards; a window whose reset time has passed restarts at 0% with a red `awaiting report` foot instead of drawing a percentage that is no longer true, and the section re-renders every minute so countdowns tick and a rollover shows without a reload; reset times and credit expiries read as countdowns (`resets in 1h 8m`), with the full instant on hover in **Asia/Shanghai**, the collector's zone and the one every calendar day here is bucketed in, since a reset rendered in the visitor's zone would disagree with the day boundaries above it; and a bar past 90% trades the vendor's brand hue for red. Banked reset credits are one tile each (hourglass + time left, soonest first, the next to lapse tinted in the plan's hue, red under a day) rather than summarised, because they are spent one at a time and which to spend depends on when the others lapse. Each subscription is a card washed faintly in its vendor's hue (`[data-p]` on the `.tk-plan`) with its mark drawn large and cropped by the corner as a backdrop, the way the Uses cards carry theirs. An empty quota list hides the section rather than explaining plumbing the reader has no stake in (the table of contents watches its targets' `hidden` attributes and drops the entry itself — `TableOfContents.astro`, so no renderer reaches into the page shell). Then an **Activity** section, where the 12-month heatmap doubles as the day picker — click a cell, or arrow-key across it (left/right a day, up/down a week, Home back to today) — for the **day panel** beneath it: four stat cards measured against the day before, then the client mix as a brand-keyed ring (`.tk-donut`, SVG arcs drawn by `day.ts`) beside a legend naming every client of that day. The legend is an accordion opened on the day's largest client, showing the models behind it, because the Breakdown section has no single-day window and this is the only place that join is readable; clicking a row or a slice opens that client instead, and the ring's centre names whichever client is open (or previewed on hover). The ring keys its slices through the rows' marks, tinted with each slice's hue, instead of a second set of chips; the top four clients get slices, and a tail of two or more merges into one grey slice (a lone tail client keeps its own). The panel opens on today and says which day it is showing; `Back to today` is the way out of anywhere else. Its freshness line reads `max(devices[].lastSeen)`, the same clock the device list shows, not `generatedAt`, which the collector rewrites on every submission including the ones that change nothing. A **Patterns** section of its own, after Breakdown, holds the eight all-time fact cards (streaks, medians, models tried, CLI-tracked active time with its tokens-per-hour rate) — they answer over the whole series rather than the selected range, which is why they sit past the range-driven sections instead of crowding the day panel. The rest of the page is range (7/30/90 days/all time) and metric toggles, stat cards with period-over-period deltas (computed client-side from the daily series), a composition bar, a trend chart stackable **by provider, client or model** (segmented toggle in the chart footer; the API's daily series carries all three slicings, and the tooltip adds a per-hour intensity line on days the CLI timed), a Mon–Sun "weekly rhythm" SVG line chart (average consumption per weekday, redrawn to container width via ResizeObserver), expandable model/client/provider breakdowns with proportional row fills and usage-span tooltips (each row's `days`/`firstDate`/`lastDate` come from the API, plus the providers a model was served through), and a device list whose rows expand to the CLI metadata (active time, longest stretch, peak concurrency, MCP servers, first seen) rather than hiding it in a `title` no touch device can reach. One `[data-p]` brand palette drives bar segments and chips (clients inherit their vendor's hue via a shared `--p` custom property; model bands take their *vendor's* hue and separate within it by `data-shade`, so a 40-odd id space needs no per-model CSS — `stackPaint`/`modelVendors` in `tokens/aggregate.ts` assign both, reading the vendor from the payload's `byModel[].providers` rather than guessing from a model's name). Device online dots age `lastSeen` against the payload's `deviceOnlineWithinMs` (a duration the collector ships, not a verdict it makes), so a locally cached payload keeps going grey on schedule. Unattributable ids (`unknown`, `<synthetic>`) are not rendered anywhere (`PLACEHOLDER_IDS`): a row reading "Other" answers no question, so they are dropped from the breakdown lists, the model disclosures, the day panel's mix and legend, the color bands and the counts of distinct things. The trade is that shares no longer quite sum to their range.

The Tokens code is layered: `Tokens.astro` owns markup, styles and skeletons only (its `<style is:global>` nests every rule under `tokens-dashboard`, because the renderers build the DOM at runtime where Astro's scoped styles cannot see it — one wrapper instead of a `:global()` on every selector). Its skeletons are sized to the payload they stand in for, not to a generic row count: two quota plans of two windows each with a reset line, `TOP_ROWS` model rows, chips under the trend chart — guessing the quota card a window short pushed the first paint down by ~200px once the data arrived, and that card is the one above the fold. The failure state (`.tk-fallback`, shown only when there is no cached payload *and* the collector did not answer) is a bordered panel with a `Try again` button rather than a sentence: the body and the fallback are the two states of one slot, so a retry puts the skeletons back and runs the load again. `tokens.astro` preloads `/api/site` (`<link rel="preload" as="fetch" crossorigin>`) so the request leaves with the CSS and JS instead of waiting for the module script to execute; the runtime controller is `src/lib/client/tokens-dashboard/` (`index.ts` mounts, loads the payload stale-while-revalidate — a locally cached copy of any age paints immediately, the revalidated answer re-renders only when `generatedAt` moved, and a failed refresh keeps the stale render instead of the fallback — reads control state (persisted for the session, and diffed against what is on screen so a change repaints only the sections it can affect), and dispatches to one renderer module per section — `quota.ts`, `activity.ts` (the heatmap and the picked day; it owns the pick, clamps it to the window on screen and hands it to `day.ts`), `day.ts` (the day panel), `overview.ts`, `trend.ts` (trend bars + weekly rhythm, each owning its tooltip), `breakdown.ts` (expandable lists), `facts.ts` (the Patterns cards), `devices.ts`, with shared DOM helpers in `dom.ts` (stat cards, delta lines, the `usageRow`/`expandableRow` breakdown rows shared by the day panel and Breakdown, brand-icon cloning, tooltip placement); all renderers are `replaceChildren`-idempotent, so a data refresh is just rendering again); the pure data layer is `src/lib/client/tokens/` — `schema.ts` (types, `SITE_SCHEMA_VERSION`, the `isSite` decoder, the range and composition tables), `load.ts` (the one `swr` fetch), `format.ts` (dates and every number-to-text rule), `aggregate.ts` (`weekdayProfile`, `windowTotals`, `computeFacts`, `stackFor` — top 3 by the metric *being drawn*, not by tokens — `activeTotals`, `dayView` — which reads the daily series rather than a range, since the series carries the client × model join that makes today and any picked day one code path, and is also where the model stacking's daily marginal is summed back out of), `labels.ts` (display names and brand icons) — re-exported whole by `src/lib/client/tokens.ts`, DOM-free, each module covered by its sibling `*.test.ts` on shared `test-helpers.ts`. The `/api/site` payload is a **versioned cross-repo contract**: the collector stamps `schemaVersion` (`SITE_VERSION` in tokens-worker) and `isSite` strictly validates every field the renderers read, rejecting any version but `SITE_SCHEMA_VERSION` (`tokens/schema.ts`; the version this build targets, also part of the localStorage cache key), so stale caches or mid-deploy mismatches refetch or fall back instead of crashing a renderer; `tokens.site-fixture.json` (a captured production payload) pins the contract in `tokens/contract.test.ts`, mirrored producer-side by `tokens-worker/test/site.spec.ts` — bump both versions together and refresh the fixture. The two repos deploy independently, so a bump has no atomic moment: the fixture has to be captured from a live endpoint already on the new schema, so **the worker ships first** and the page falls back for the couple of minutes in between. Closing that window — letting `isSite` accept the previous version too, shipping this repo first, then dropping it again — only works for a shape the current reader survives, and it is a deploy manoeuvre, not a standing allowance. The AI brand icons on breakdown rows are mono SVGs from [Lobe Icons](https://lobehub.com/icons) vendored under `src/assets/icons/ai/` (slug mapping in `aiIcon()`), stripped of their `<title>` — the defs block is cloned into rows that carry their own `title` tooltip, which a nested SVG `<title>` would shadow.

`Memos.astro` (on `/memos`) renders the Mastodon statuses (`MASTODON` in `consts.ts`, boosts/replies excluded) as a **thread** the same way: one hairline runs down the left edge, each memo is a hollow node on it (filled on hover) and each year opens with a larger filled node carrying the year as an `h2` (`renderYear`, inserted by `index.ts` wherever the year changes), so the entries' date labels drop the year (`JUL 20`). Each entry draws the stretch of line from its own top to the next entry (`--gap-after`), so no piece has to know where another sits, and the last one fades out since the account goes on past what is shown. The uppercase date sits in a rail column (linking to the original status, full timestamp on hover, sticky beside a long entry at `>= 40rem`, folding above the content below it), with the sanitized content and a 1/2/3/4-up media grid with `srcset` from the attachment metadata on the right — a single attachment renders at a fixed max height with its width following its own ratio, so one shot never fills the column. Video and `gifv` attachments render as `<video>` inside the same grid (gifv autoplays muted and looping unless `prefers-reduced-motion`, everything else gets a poster and controls), audio plays on its own row below it, and a status carrying a content warning folds behind a `<details>` — the whole entry under `spoiler_text`, or just the media when it is merely `sensitive`. It follows the Tokens layering: the pure data layer is `src/lib/client/memos.ts` (status → memo normalization on top of `safeHttpUrl`, custom-emoji tokenization, attachment/srcset selection, the grid's `sizes`; covered by `src/lib/client/memos.test.ts`) and the runtime controller is `src/lib/client/memos-feed/` (`index.ts` mounts and loads through the shared session cache, distinguishing an empty account from a failed load; `render.ts` builds entries; `sanitize.ts` is the allow-list HTML sanitizer — it needs `DOMParser`, which is why it can't live in the pure layer — keeping remote status HTML down to inline tags, http(s) links and Mastodon's four presentation classes), leaving `Memos.astro` with markup, styles and skeletons only.

`Switch.astro` (on `/misc`) renders Nintendo Switch play activity from the sibling `switch-worker` repo (`SWITCH` in `consts.ts`, endpoint `https://switch.lkwplus.com`), another single precomposed `/api/site` behind a `schemaVersion` contract — `SITE_SCHEMA_VERSION` in `src/lib/client/switch.ts`, pinned against `switch.site-fixture.json`, bumped in lockstep with the worker's `SITE_VERSION` (worker ships first; see the same note for Tokens above). The section is all-time stats, the shared heatmap, and **the catalog ranked by lifetime play time** — not a recently-played list, which answers "what did I touch last" rather than "what am I actually playing". **The list is the chart**: every row is one bar — its own background, a `linear-gradient` filled to the title's share of the most-played one (`--total`), with the part inside the last-`recentDays` window (`--recent`) drawn in the heatmap's green, so the "played lately" colour means the same thing in the grid above and in the list. A row is a two-digit rank, a cover, the title over its recency line (`… in 14d` when the recent window is only part of the history), and the lifetime hours at the far end — one line each, the title ellipsed with the full name on hover, so every row is exactly the cover's height and its skeleton reserves it to the pixel. There is deliberately no legend over the list: the green reads as the recent share on its own, and the rows that are actually split already say so in words, which is why that clause suppresses itself while a title's recent minutes are its whole history — a split that isn't split explains nothing. Recency is `lastPlayedLabel()` — days counted back from the payload's own `today`, not a date, because on a list ranked by lifetime hours the question is whether a title is still in rotation. Every render *decision* — which four cards (`statCards()`, whose third card is Library value or Days active), what the line under a title says (`rowFoot()`) — lives in `switch.ts` and is covered by `switch.test.ts`, so a refresh that flips a state (prices gone, bars no longer split) is pinned by a unit test; `Switch.astro` only writes those strings into the DOM. The payload carries no per-game day count or first-played date for the same reason: how long ago it started answers nothing this list asks. The third all-time card is **Library value**, `stats.libraryValueCny` formatted `zh-CN` so the sign is a bare `¥`, with the currency and the priced-title count in its `title` — prices are best-effort, so a payload with none falls back to Days active rather than showing a dash. The eShop link covers the row rather than sitting in it (the whole row is the hit target) and stays transparent so the bar shows through it; the row itself takes the faint `--muted` hover wash the Music rows and Movies cards use. `activity` from the worker is dense but starts at the first played day; `heatmapWindow()` pads it out to `HEAT_MAX_WEEKS * 7` days ending today, because padding is a rendering concern and the payload should only claim the range it tracked — a short series is what made the grid render two cells floating in an empty frame. All artwork URLs point at `img.lkwplus.com`: the worker mirrors Nintendo's CDN into R2 at sync time, so nothing here hotlinks. Prices and titles are the worker's too — the znma API has neither a price nor a consistent name (it reports whatever *that console* calls a game, which is one language per title), so the worker reads the HK product page for the price and the US one for the name, once per title, and converts at one ECB rate per sync; the page only ever sees the summed total and how many titles are behind it. **Playtime here is time in games**, from the worker's `daily_games` — a console total also counts the HOME menu and the eShop, so it would disagree with the list it sits above.

`Flights.astro` (on `/misc`) maps the flights logged in the self-hosted [AirTrail](https://github.com/johanohly/AirTrail) instance, read through the sibling `flights-worker` repo (`FLIGHTS` in `consts.ts`, endpoint `https://flights.lkwplus.com`; the worker holds the AirTrail API key as a secret, so the key never reaches this repo or the browser). Another precomposed `/api/site` behind a `schemaVersion` contract — `SITE_SCHEMA_VERSION` in `src/lib/client/flights.ts`, pinned against `flights.site-fixture.json`, bumped in lockstep with the worker's `SITE_VERSION` (worker ships first). **The payload is the map, not the log**: airports (with visit counts), routes (airport pairs in code order, flown-either-way merged, with flight count, upcoming count, great-circle km and mean minutes), airline and aircraft tallies, and totals — no single flight, flight number or per-flight date, because the section deliberately shows where, not when. The section is an eight-cell readout (four totals, then routes / longest / airlines / aircraft, each footed by what leads it — `statCards()`, a tie at the top names nobody), the globe, and two ranked lists under it (airports by visits, routes by flights, `limit` rows each, each row a bar filled to its share of the leader like the Switch list). The globe is Cobe 2 with an **overlay** drawn in SVG/HTML over the canvas: `toVector`/`arcPoint`/`project` in `flights.ts` are Cobe's own vertex math (its location vector, the arc shader's quadratic curve, its projection), unit-tested so that turning to a place projects it onto the centre — that agreement is what makes the trail land on the arc Cobe drew. It **tours the routes**: turns to each in turn, draws a trail along the arc with a plane at its head, pulses both ends, labels each end with its code over its city, above the airport and on the side away from the other end (so a label lies across neither its route nor the ones fanning out below a hub), and puts what the labels leave out — distance, mean time, flights — in one centred line under the globe (`.flights-caption`), over a short rule that fills while the tour dwells. Pointing at (or focusing) a list row takes the tour over — a route row flies that route, an airport row turns to the airport and lights every route out of it — and leaving hands it back to where the tour was. Drag rotates the globe; the loop stops when settled or off screen. Colours are per-theme palettes in the component (Cobe draws arcs and markers opaque, so a dimmed one is a colour mixed toward the page); in light mode keep `mapBrightness` under 1, since Cobe shades a light-mode dot `1 − brightness` and anything above saturates the map to black.

`Lightbox.astro` is the shared click-to-zoom for content images (blog post pages and `/memos`), backed by **PhotoSwipe**. The eager part (`src/lib/client/lightbox.ts`) is only a click delegate that assembles slide data; PhotoSwipe itself (JS + CSS) code-splits into a chunk fetched on first use, and the open/close animation zooms from the clicked thumbnail via the `thumbEl`/`placeholderSrc` filters (largest `srcset` candidate or the memo permalink as the full-size source). Zoomable = bare `prose-content` images (never the inline custom emoji), `post-banner`, and `.memo-shot` cards — a multi-image memo opens as one swipeable gallery; other linked images keep their navigation. Drop the component on a page to enable it.

All six feeds share `src/lib/client/feed.ts`: the Web Storage cache with two reading disciplines — `cached()`, the 60 s TTL in sessionStorage used by Music/Movies/Memos, and `swr()`, the stale-while-revalidate path used by Tokens, Switch and Flights (paint any cached copy, always refetch, deliver the network answer to the same callback; the endpoint makes the refetch cheap via ETag/304). `swr()` persists to **localStorage**, since a discipline that already accepts a copy of any age has no reason to forget it when the tab closes — a new tab or next week's visit paints from the last payload instead of skeletons. Its keys carry the schema version (`tokens:site:v14:…`), and the writer sweeps the same feed's entries under any other version, which is what keeps a version bump from leaving the previous build's payload behind for good. Both disciplines validate payloads **before caching and before use** (a bad payload rejects into the feed's fallback UI), the decoder primitives those validators are built from (`isRecord`, `isCount`, `isCalendarDay` — the Tokens, Switch and Flights decoders import them rather than each keeping a copy), the fetch timeout, and `safeHttpUrl()`, the trust boundary that keeps remote-payload hrefs/image URLs (Letterboxd, Mastodon) from injecting non-http(s) URLs into the DOM. The element factory every renderer builds DOM with is shared too — `el()` in `src/lib/client/dom.ts`, re-exported by the Tokens `dom.ts`. The GitHub-style activity heatmap is shared as well: `Heatmap.astro` owns the markup, the green palette, and the `--heat-cell`/`--heat-gap` geometry (single source of truth — `src/lib/client/heatmap.ts` reads the computed values), and `heatmap.ts` owns the fit-to-width renderer (`mountHeatmap`) that Music, Tokens and Switch feed with their own level scales — its `days` contract is *dense and chronological*, which is a caller's obligation, not something it repairs. Every cell carries its `data-date`, and `<Heatmap selectable />` (Tokens) adds the pointer affordance, a focusable grid and the ring on `[data-selected]` — an *inset* one, since `.heat-grid` clips its overflow — so the picker is the caller's event delegation over cells the grid already labelled, not a second heatmap. The fixed-length `/misc` lists — Movies, Music, Switch, the Flights rankings — render one skeleton per row they will fill (`limit`), each placeholder built to the loaded row's exact height (reserved two-line titles, `min-block-size: 1lh` on lines whose skeleton bar is shorter than the text), because anything short of the final height shifts every section below it when the data lands. `SKELETON_ROWS` (3, in `src/lib/utils.ts`) is left for feeds that can't know their height — Memos (whose skeleton opens on a year marker, as the loaded thread always does) and the Tokens devices. Tokens is the exception on purpose — it is a whole page whose first section sits above the fold, so its skeletons are sized to the payload (see above) and the trade goes the other way.

`/about` shows build-time blog stats (posts, CJK-aware word count, tags, first-post year) computed in `about.astro`'s frontmatter.

Shared feed typography and skeleton geometry live in `src/styles/feed.css`, imported by `Layout.astro` — including the **readout** every summary grid shares (`dl.readout`: Music and Switch all-time stats, the Flights totals, the Tokens day/overview/Patterns cards). It is not a boxed panel: each cell is a label over a large figure over a dim foot line, headed by a hairline rule with a short accent tick on it (`--readout-accent`, green by default, Switch red, Flights amber). The rule and tick draw in, staggered by cell (`--i`), the first time the panel is ≥35% on screen (`data-seen`); hovering a cell runs its tick across the rule and fades a wash up behind it. Values go through `setReadout()` (`src/lib/client/readout.ts`, pure half covered by `readout.test.ts`), never `textContent`: it splits a figure into number and unit runs (`145.1M`, `12h 30m`, `¥3,450` — units set small, a figure with no digits at full size via `data-word`), counts the numbers up the first time the panel is seen and from the old value to the new one when a render changes it (only when the shape is unchanged — `145.1M` → `1.2B` counts from zero rather than through `140B`), and writing the figure already shown is a no-op, which is what keeps a stale-while-revalidate repaint from making the numbers jump. It is two across or four, never three, switched on the panel's own width by a `clamp()` in its `minmax()` against `--panel-wide` — so no container query — and Tokens raises that threshold to `44rem`, because its cells carry a comparison line that must not wrap: a wrapped line is one its skeleton didn't reserve. Movies is a poster wall (title and year under the artwork in a two-line block, stars and a short date under that, `Rewatch` as a solid tag on the poster's corner); a card answers hover with the same faint `--muted` wash as the Music rows — the artwork does not move, and the title is not underlined. Music's last-played list leads with its newest listen as a sleeve with a record half out of it — the record's label printed with the cover art and always turning, a green dot before the time while the play is under ten minutes old — and runs the rest in intrinsic `auto-fill` columns — which is why `/misc` asks it for 11 listens: the ten after the lead fill two columns evenly. Each feed keeps its row layout and distinct spacing in its component. Switch delivers cached and refreshed data to the same idempotent renderer.

`Uses.astro` (on `/misc`) is the one section there with no runtime at all — static build-time hardware from `USES` in `consts.ts`, grouped by where a thing lives (Desk, Carry) rather than by product class, since where it sits says more about how often it gets touched. It borrows the feeds' intro and uppercase label treatment from `feed.css` (`.uses-intro`/`.uses-label` sit in the same selector lists as the Music/Switch/Tokens ones) so the section reads as part of the page rather than a fifth copy of the same rules, and keeps the label bare as each group's header — the cards under it already mark where a group starts and ends, so a rule and a count beside it only repeated them. The section spaces itself with grid gaps only, so no edge has a margin to undo.

Each thing is a **card in a bento grid** — `USES` carries an `icon` from the `UsesIcon` union and `Uses.astro` maps it through a `Record<UsesIcon, …>` of vendored [Lucide](https://lucide.dev) SVGs in `src/assets/icons/uses/` (same shape as the other icons here: `1em`, `currentColor`, no `<title>`), so an icon named in the data with no SVG behind it fails the build instead of rendering an empty card. The mark is not a chip beside the name but the card's backdrop: drawn large, at 9% of the foreground, thinned to a 1.25 stroke via CSS on its `g`, and cropped by the card's bottom-right corner (it tilts a few degrees on hover, motion permitting). It lives in the `dt` because a `dl > div` admits only `dt`/`dd`, but it is positioned against the card, so its place in the markup costs nothing. The first thing in a group is its anchor — two cells wide, a size up in name and mark — and a group left one cell short hands the gap to its last card (`:last-child:nth-child(even)`), so groups of four and five fill their rows at both two and three columns without a size field in the data. A group of another size may leave a hole; revisit the rule rather than the data if one ever does.

The grid is two columns, and three via a **container query** (`container-type: inline-size` on `uses-list`, `@container (width >= 34rem)`), not a viewport one: between 64rem and 76rem the sidebar and the table of contents take their cut of the page grid first, so a viewport query would widen the grid while the column itself is still narrow. The Movies poster wall uses a container query for the same reason (three posters across, four at `>= 30rem` of column); these two are the only ones in the codebase, and that asymmetry is the reason for both.
